1 Introduction
1.1 Purpose
This document defines the requirements for NexusChat, a lightweight web-based chat application built
as a student/academic project. It is scoped to two core chat experiences, plus three focused AI-assisted
utilities (summarization, translation, and search), so the project remains achievable for a solo or small-
team build while still demonstrating real-time systems, database design, and Generative AI integration.
This document is written so any reader — a classmate, instructor, or evaluator — can understand
exactly what the app does and does not do, without needing further explanation.
1.2 Scope
NexusChat provides exactly two chat modes, each supported by the same three AI utilities:
● Temporary Chatroom — a multi-user room that anyone can be invited to, supports text and media
sharing, and is automatically (or manually) destroyed when the admin deletes it or all members go
offline. Before it disappears, an AI-generated summary of the conversation is posted into the room
as a system message for every member to see.
● Private Chat — a simple one-to-one conversation (WhatsApp-style) that persists indefinitely. Either
user can manually delete the conversation, or both users can opt into a recurring 24-hour auto-
reset that clears the chat automatically.
Both chat modes additionally support:
● AI Translation — any message can be translated into a user's preferred language on request.
● Message Search — users can search within a chatroom or a private chat by word or sentence to
locate past messages.
● Message Actions — a sender can delete/unsend, edit (text only), copy, or forward their own
messages.
● Reactions & Stickers — users can react to any message with an emoji, and send static stickers as
their own message type.
Everything outside these seven capabilities — group admin hierarchies, friend/contact systems, message
pinning, reply-to threading, smart replies, animated/custom stickers, voice/video calling, and similar
additions — is explicitly out of scope for this version. This keeps the build small enough to finish and
defend as a course project.

3.1 Technology Stack
The stack below is fixed per the constraints in Section 2.4 — a single Python backend, Supabase for both
database and storage, and Gemini as the AI provider.
Layer Technology
Frontend React + TypeScript (Vite)
Backend / API Python — FastAPI
Real-time transport WebSockets (via FastAPI's native WebSocket support)
Authentication JWT (Supabase Auth, or a custom JWT layer — either is acceptable)
Database Supabase (managed PostgreSQL)
Media storage Supabase Storage
Message search PostgreSQL full-text search (tsvector/tsquery), native to Supabase
AI provider Gemini API (Flash model) — summarization and translation
Why Gemini over Groq
Both are free to use for a student project. Gemini is recommended here because summarization and
translation are language-quality-sensitive tasks, and Gemini's free tier offers a substantially higher daily
request volume alongside strong native multilingual support — a good fit for both AI features this project
needs. Groq is optimized primarily for raw inference speed on open-source models, which matters less here
than output quality. Either provider can be swapped in with minimal code change, since both expose a simple
prompt-in/text-out API.
This remains a small stack overall — no message queue, no caching layer, no microservices, and no
separate search engine. A single Python backend and Supabase's built-in capabilities are enough at this
scale.

5 Feature 1 — Temporary Chatroom
5.1 Description
A chatroom is a multi-user space created by one user (the admin), who can invite other users to join.
Members exchange text and media in real time. The room is temporary by design: it is destroyed either
when the admin deletes it, or automatically when every member has gone offline. Immediately before
the room disappears, the system posts an AI-generated summary of the conversation as a special system
message, visible to every member who was present.

9 Feature 5 — Message Actions
9.1 Description
Available in both the chatroom and private chat, message actions cover the small set of per-message
conveniences users expect from a standard chat app: deleting/unsending a sent message, editing a sent
text message, copying a message's text, and forwarding a message to another chat. All four actions
apply only to messages the requesting user themselves sent, except copy and forward, which may be
performed on any message the user can view.
ID Requirement
The system shall allow a user to delete (unsend) their own message from a chatroom or
FR-8.1
private chat, removing it for all participants.
The system shall allow a user to edit the text content of their own previously sent text

The system shall not allow editing of media messages (images, video, audio, documents)

FR-8.4

FR-8.5

10 Feature 6 — Reactions & Stickers
10.1 Description
Available in both the chatroom and private chat, this feature adds two lightweight, expressive tools on
top of ordinary text and media messages: emoji reactions attached to an existing message, and static
stickers sent as their own standalone message. The two are distinct — a reaction decorates a message
someone already sent, while a sticker is itself a new message, chosen from a fixed sticker pack and
posted into the chat like any other message.
10.1.1 Emoji Reactions
Any user in a chat can react to any message with an emoji from a standard set (for example: thumbs up,
heart, laugh, surprised, sad). A message can carry multiple reactions from multiple users, and each
user's reaction is visible to all participants.
10.1.2 Static Stickers
A sticker is sent as a distinct message type, selected from a fixed, pre-defined sticker pack bundled with
the app. Stickers are static images (not animated) and are sent standalone — a sticker message has no
accompanying text.
10.2 Requirements
ID Requirement

The system shall allow a message to carry multiple reactions from multiple different users

FR-9.3 The system shall allow a user to remove their own reaction from a message.
The system shall display all reactions on a message, along with which users placed them,
FR-9.4

The system shall allow a user to browse a fixed, predefined sticker pack and send a static
FR-9.5

The system shall deliver reactions and sticker messages in real time via WebSocket,

The system shall support reactions and stickers identically in both chatroom and private

Design Note
Stickers are static image assets bundled with the app rather than user-uploaded content — there is no sticker
creation, custom pack, or animated sticker requirement in this version. This keeps the feature to a fixed asset
list plus one new message_type value, rather than a full content-management system.

NexusChat — Software Requirements Specification
16 Out of Scope
To keep this achievable as a student project, the following are explicitly not included in this version:
● Friend/contact system, friend requests, blocking
● Group admin hierarchies beyond a single room-admin role
● Message pinning or reply-to threading
● Editing of media messages (edit is text-only, per Section 9.1)
● Animated stickers, custom sticker uploads, or user-created sticker packs — only a fixed, static, app-
bundled pack
● AI features beyond summarization, translation, and search (no Ask-AI or smart replies)
● Voice or video calling
● Push notifications outside the app
● Cross-chat or global search — search is scoped to one chat at a time
Any of these can be added later as extensions once the core build is complete and stable.

NexusChat — Software Requirements Specification
17 Success Criteria
The project will be considered complete when it:
● Supports secure registration, login, and logout.
● Allows creating a chatroom, inviting members, and real-time messaging with media sharing.
● Correctly deletes a chatroom when the admin removes it, or when all members go offline.
● Generates and delivers an AI summary — both on-demand and automatically at room expiry —
with chatroom name, members present, and timestamp.
● Supports a persistent one-to-one private chat with real-time messaging and media sharing.
● Allows manual deletion of a private chat by either participant.
● Supports a mutually-agreed, recurring 24-hour auto-reset for a private chat, toggleable by either
user.
● Allows translating any message, in either chat mode, into a user's preferred language.
● Allows searching by word or sentence within a chatroom or private chat's message history.
● Allows a sender to delete/unsend or edit (text only) their own messages, with changes reflected in
real time for all participants.
● Allows any viewable message to be copied or forwarded to another chat.
● Allows any user to react to a message with an emoji, and to send static stickers from a fixed pack as
standalone messages.
● Runs on an all-Python backend with Supabase as the sole database and storage provider.
● Is deployed and accessible for demonstration or evaluation.
Document Note
This is a deliberately narrow SRS. Resist the urge to add features mid-build — the current scope is what makes
this finishable. Anything from the Out of Scope list is a good "future work" talking point for a project writeup,
without needing to actually build it.
